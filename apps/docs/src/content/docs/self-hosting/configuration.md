Warden's settings live in `infra/production/.env` on the server. Edit them there, then apply:

```bash
cd ~/warden/infra/production
nano .env
sudo docker compose up -d
```

`up -d` recreates only the containers whose settings changed.

:::danger[Settings you never change]
`MASTER_KEY`, `POSTGRES_PASSWORD`, `JWT_ACCESS_SECRET` and `JWT_REFRESH_SECRET` were generated by the installer. Changing `MASTER_KEY` after Warden has stored anything makes every stored secret unreadable.
:::

Keep `.env` off chats, tickets and screenshots. If a value leaks, replace it at its source (Resend, GitHub, your storage provider) and update the file.

## Email

Sign-in links, invitations, password-reset codes and alerts.

```ini
RESEND_API_KEY=re_...
MAIL_FROM=Warden <noreply@example.com>
MAIL_SUPPORT=support@example.com
```

Warden sends through [Resend](https://resend.com). `MAIL_FROM` must use a domain you've verified in Resend: add the DNS records Resend lists for the domain (DKIM, SPF and MX on a `send` subdomain), plus a DMARC record such as `v=DMARC1; p=none`. `MAIL_SUPPORT` is your support inbox: it appears as "Questions?" at the bottom of every email, and turns on the dashboard's **Support** button, whose messages (with up to 3 screenshots) are emailed there with the sender as Reply-To. Leave it empty and the Support button is hidden.

Without `RESEND_API_KEY`, nothing is sent and links appear in the API's log instead.

## Sign in with GitHub

```ini
GITHUB_CLIENT_ID=
GITHUB_CLIENT_SECRET=
```

These can come from the Warden GitHub App (below) or from a separate GitHub OAuth App. Either way:

- Its callback URL is `https://<your domain>/api/auth/github/callback`.
- Warden reads the user's verified email address. If you use the GitHub App, give it the **Account permissions → Email addresses: Read-only** permission.

Leave both empty to offer email sign-in only.

## The Warden GitHub App

Needed for private repositories and for deploying on every push. Public repositories work without it.

```ini
GITHUB_APP_ID=
GITHUB_APP_SLUG=
GITHUB_APP_WEBHOOK_SECRET=
GITHUB_APP_PRIVATE_KEY=
```

Create it at **GitHub → Settings → Developer settings → GitHub Apps → New GitHub App**:

| Field | Value |
|---|---|
| Homepage URL | `https://<your domain>` |
| Setup URL | `https://<your domain>/api/github/callback`, with **Redirect on update** ticked |
| Request user authorization during installation | Off (it would disable the Setup URL) |
| Webhook URL | `https://<your domain>/api/github/webhook` |
| Webhook secret | A random value (`openssl rand -hex 32`); the same value goes in `GITHUB_APP_WEBHOOK_SECRET` |
| Repository permissions | **Contents: Read-only** (Metadata: Read-only is added by GitHub) |
| Events | **Push** |

Then:

- `GITHUB_APP_ID` is the **App ID** on the App's page, and `GITHUB_APP_SLUG` is the name in its public link (`github.com/apps/<slug>`).
- Under **Private keys**, generate a key. It downloads as a `.pem` file. `GITHUB_APP_PRIVATE_KEY` needs it on **one line**, with `\n` for the line breaks. On a Mac this copies it in that form:

  ```bash
  awk 'NF {sub(/\r/, ""); printf "%s\\n",$0;}' ~/Downloads/<app>.private-key.pem | pbcopy
  ```

After `docker compose up -d`, connect it from the dashboard: **Settings → GitHub**.

## Backup storage

Warden's own bucket for database backups, and for backups of Warden's own database (see [Updates and backups](/self-hosting/updates-and-backups/)). Any S3-compatible store works; Cloudflare R2 is a good fit.

```ini
BACKUP_S3_ENDPOINT=https://<account id>.r2.cloudflarestorage.com
BACKUP_S3_BUCKET=warden-backups
BACKUP_S3_ACCESS_KEY_ID=
BACKUP_S3_SECRET_ACCESS_KEY=
```

Use a bucket of its own (not one shared with a development copy of Warden) and an API token limited to that bucket. Organizations can also bring their own bucket from **Settings → Backup storage**, which takes priority for their databases.
